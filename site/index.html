Qaysi signallar eskalatsiya qilinadi?Which alerts get escalated?

Moliyaviy monitoring xakatoni uchun EDA va model. Jamoa SSUZ7K.EDA and a model for the financial monitoring hackathon. Team SSUZ7K.

Monitoring bo'limiga mijozlarning tranzaksiya tarixidan avtomatik signallar keladi. Mutaxassis har birini ko'rib chiqadi: yo rad etadi, yo eskalatsiya qiladi. Bizning vazifa: yashirin test to'plamidagi har bir signal uchun eskalatsiya ehtimolini berish. Baholash ROC-AUC bo'yicha. A monitoring unit gets automatic alerts generated from customers' transaction histories. A specialist reviews each one and either dismisses it or escalates it. Our job: give every alert in the hidden test set a probability of being escalated. Scoring is ROC-AUC.

Eng yaxshi natijamiz: CV ROC-AUC 0.650 (5 fold × 3 marta takror; foldlar bo'yicha 0.648 ± 0.013).Our best result: CV ROC-AUC 0.650 (5 folds × 3 repeats; per fold 0.648 ± 0.013).

Rostini aytsak, bu raqam juda baland emas. Quyida nima uchunligini va nimalarni sinab ko'rganimizni yozdik.Honestly, that number is not high. Below we explain why, and what we tried along the way.

Ma'lumotlar sintetik, haqiqiy mijozlar yo'q. Oxirgi yangilanish: 2026-09-24.The data are synthetic, no real customers. Last updated 2026-09-24.

Qanday ishladikHow we approached it

raw files → audit → EDA → features (1 row / alert) → CV 5×3 → LightGBM · XGBoost · CatBoost · LogReg → blend check → submission

Avval ma'lumotni tekshirdik (dublikatlar, bo'sh qiymatlar, signaldan keyingi tranzaksiyalar). Keyin har bir signal uchun faqat signal sanasidan oldingi tranzaksiyalardan 626 ta belgi yig'dik. Modellarni bir xil CV bo'linishlarida solishtirdik va biror g'oyani faqat CV natijasini yaxshilasa qoldirdik. Hamma seed'lar qotirilgan, butun jarayon bitta buyruq bilan qaytadan ishlaydi. First we checked the data (duplicates, nulls, transactions after the alert). Then for each alert we built 626 features using only transactions from before the alert date. All models were compared on the same CV splits, and an idea stayed in only if it improved the CV score. Seeds are fixed and the whole thing re-runs with one command.

Bir signalga o'rtacha 499 ta tranzaksiya to'g'ri keladi (median 461), odatda signalgacha bo'lgan oxirgi ~180 kun. Signal sanalari train'da ham, test'da ham 2025-01-01 dan 2026-12-31 gacha. Bo'sh qiymat, takroriy ID yoki "yetim" tranzaksiya topilmadi. An alert has 499 transactions on average (median 461), usually covering the last ~180 days before the alert. Alert dates run from 2025-01-01 to 2026-12-31 in both train and test. We found no nulls, no duplicate IDs and no orphan transactions.

Sizib chiqish (leakage) bilan ehtiyot bo'ldikBeing careful about leakage

  • Signal sanasida vaqt yo'q, shuning uchun signal momentini o'sha kunning 00:00 deb oldik. Shundan keyingi 3 934 (train) va 1 456 (test) tranzaksiyani belgilardan chiqarib tashladik.The alert date has no time, so we treat the alert as happening at 00:00 that day. The 3 934 (train) and 1 456 (test) transactions at or after that moment are not used.
  • signal_id modelga berilmaydi. Tekshirib ko'rdik: ID tartibi bilan maqsad orasidagi AUC 0.498, ya'ni bog'liqlik yo'q.signal_id is never given to the model. We checked anyway: ID order vs target gives AUC 0.498, i.e. nothing.
  • Train va test'ni ajrata oladigan model qurdik (adversarial validation): AUC 0.502. Demak test oddiy tasodifiy tanlanma.We trained a model to tell train from test (adversarial validation): AUC 0.502. So the test set is just a random sample.

Model va validatsiyaModel and validation

Test sanalari train bilan bir xil oraliqda, adversarial AUC 0.5 atrofida. Shuning uchun vaqt bo'yicha bo'lish shart emas edi va biz takroriy stratifikatsiyalangan 5-fold ishlatdik (3 marta, seed 42). Imputatsiya, masshtablash va erta to'xtatish faqat o'quv fold ichida. Giperparametrlarni Optuna bilan topib, keyin qotirib qo'ydik. Test dates cover the same range as train and adversarial AUC is around 0.5, so a time-based split was not needed. We used repeated stratified 5-fold CV (3 repeats, seed 42). Imputation, scaling and early stopping only ever see the training fold. Hyper-parameters were tuned with Optuna and then frozen.

XulosaWrap-up

Eskalatsiya signali kuchsiz va juda ko'p belgilar orasida tarqalgan. Eng yaxshi bitta belgi ham AUC 0.58 ga yetmaydi, lekin yuzlab kuchsiz belgilarni birga ishlatgan gradient boosting 0.650 beradi. Eng aniq ko'ringan narsa: eskalatsiya qilingan mijozlarda mayda bank o'tkazmalari ko'proq, yiriklari kamroq, va ular umuman olganda biroz faolroq (~6%). Tungi operatsiyalar, dam olish kunlari, "kirdi-chiqdi" (pass-through) va strukturalash kabi klassik AML belgilarini tekshirdik, lekin ular bu ma'lumotda ishlamadi. The escalation signal is weak and spread over a lot of features. No single feature reaches 0.58 AUC, but gradient boosting over hundreds of weak ones gets to 0.650. The clearest thing we can point at: escalated customers make more small bank transfers and fewer large ones, and are a bit more active overall (~6%). We checked the classic AML red flags too (night activity, weekends, pass-through, structuring), and none of them worked on this data.

Cheklovlar. Kontragent va mijoz ID'si yo'q, shuning uchun graf belgilarini qura olmadik. Miqdor standartlashtirilgan indeks. Signal oldidagi 3 daqiqalik "portlash" generatorning artefakti bo'lsa kerak. GitHub'dagi boshqa jamoalarning ochiq natijalari ham 0.56 va 0.63 orasida, demak shift asosan ma'lumotning o'zida. Limitations. There are no counterparties or customer IDs, so no graph features. Amounts are a standardised index. The 3-minute burst before each alert is most likely a generator artefact. Other teams' public results on GitHub sit between 0.56 and 0.63, which suggests the ceiling is mostly in the data itself.

Vaqt bo'lsa nima qilardik: CoLES kabi o'z-o'zini o'rgatuvchi ketma-ketlik embeddinglari; kontragent ma'lumoti bo'lsa, graf belgilar.With more time we would try self-supervised sequence embeddings (CoLES), and graph features if counterparty data existed.
